Sfincs Web launcher guide

Reichen Schaller

The Sfincs intro tab is for someone brand new to SFINCS. The other tabs are for learning how to use each launcher mode, including manual setup, override runs, batch generation, the guided wizard, and run comparison.

Manual

Manual Mode is the direct configuration workflow. Use this guide section when you want to understand what each Manual tab, field, and action button means before creating or testing a run.

This section mirrors the real Manual Mode tabs. Each guide tab explains what that part of the page is for, what the controls mean, when to change them, and what mistakes to avoid.

0 — Run identity

The Run identity tab names the run and decides where the run folder will be written. These fields do not change the physics of the model, but they are important because they control how the run is organized, saved, and protected from accidental overwrite.

A good run identity should make the run recognizable later. Use names that describe the event, experiment, version, or test purpose without depending on one specific computer or one temporary folder layout.

Field / preview What it means How to use it safely
event_name A short label for the event, storm, scenario, or test case. Use this as a human-readable label. It helps organize runs, but the actual folder name is controlled by run_name.
run_series A label for a group of related experiments. Useful when testing several versions of the same event, resource setup, forcing setup, or model configuration.
run_name The folder name for this specific run. Keep it unique and simple. Use letters, numbers, underscores, dashes, and periods. Avoid spaces and vague names like test.
project_root The pipeline or launcher project folder used by the backend. Most users should leave this at the current shared project or deployed pipeline location. Change it only when deliberately testing another pipeline bundle.
output_root The parent folder where run folders are created. Choose a location meant for run outputs. Avoid mixing finished model outputs into source-data or code folders.
planned run root A preview of the final run folder path, computed from output_root and run_name. This is a preview only. Check it before preflight/build/submit so you know exactly where the run will go.
overwrite_existing_run Allows the backend to replace or reuse an existing run folder. Keep this false unless you are intentionally replacing a scaffold or rerunning into a known folder. A finished run folder should not be overwritten casually.
allow_writes_inside_proj Controls whether the backend may write inside a shared project-style folder. Use the setting that matches the deployment. Shared project deployments may allow this; personal scratch workflows may keep it off.
allow_missing_model_inputs Lets some missing model inputs become warnings instead of hard stops. Real runs should normally keep this false. Only relax it for skeleton tests or deliberate backend debugging.
run_description A short plain-language description of the run. Use this to record why the run exists, especially when comparing several similar runs later.
run_tags A JSON list of labels saved with the config. Use simple tags like mode, event type, project name, or experiment family. Keep valid JSON syntax.

Safety note: Preflight can be useful for checking an imported or older config, but passing preflight does not prove the destination folder is safe to build or submit into. Build Scripts and Submit should still protect real existing run folders unless overwrite behavior is intentionally enabled.

1 — Pipeline

The Pipeline tab chooses which stages of the workflow should be included when the run is built or submitted. A normal full run has three stages: preprocessing, SFINCS, and postprocessing.

These switches are useful for testing. For example, you may want to run only preprocessing while debugging input generation, or skip postprocessing while testing whether the model itself completes.

Field What it controls Recommended use
run_preprocessing_job Controls whether the preprocessing stage is included. Usually true. Turn it off only when you already have the needed model inputs and are intentionally testing a later stage.
run_sfincs_job Controls whether the SFINCS solver stage is included. Usually true for real model runs. Turn it off only for scaffold, preprocessing, or postprocessing-specific tests.
run_postprocessing_job Controls whether the postprocessing stage is included. Usually true when you want maps, summaries, plots, or quicklooks after the model finishes.
submit_with_dependencies Controls whether later jobs wait for earlier jobs. Normally true. This prevents the solver from starting before preprocessing succeeds, and prevents postprocessing from starting before model output exists.
dependency_type The Slurm dependency rule used between stages. The normal dependency style is afterok, meaning the next stage starts only if the previous stage exits successfully.

Manual Mode rule: Manual Mode should stay a clean manual/HydroMT-build workflow. Native-file override workflows belong in Override Mode unless you are deliberately debugging backend behavior.

2 — Slurm general

The Slurm general tab contains scheduler settings that apply to the generated job scripts. These settings do not change the flood model physics, but they affect how the cluster queues, runs, and reports the jobs.

Most users should leave these fields blank or at the provided defaults unless the cluster, lab, or project requires specific scheduler options.

Field What it means How to use it safely
slurm_account The Slurm account charged for the jobs, when the cluster requires one. Leave blank unless your project or cluster instructions tell you to use a specific account.
slurm_partition The cluster partition or queue where jobs should run. Leave blank for the default partition unless you know a specific partition is required for this run.
slurm_qos The quality-of-service setting, if your cluster uses one. Leave blank unless needed. A wrong QOS can cause submission failure or unexpected queue behavior.
slurm_email An optional email address for Slurm job notifications. Use only when you want email updates. Leaving it blank keeps email notifications off.
slurm_mail_type Which job events should trigger email notifications. Only matters when slurm_email is set. Common values notify when jobs end or fail.
slurm_extra_directives A JSON list of extra scheduler directives to add to generated scripts. Usually keep this empty. Add directives only when you understand the scheduler option and the JSON syntax.
bash_strict_mode Controls whether generated shell scripts use stricter error handling. Keep true for normal runs. Turn it off only while debugging unusual shell behavior.

Cluster note: resource size belongs mostly in the next tab, Stage resources. This tab is mainly for scheduler identity, queue behavior, optional notifications, and extra scheduler lines.

3 — Stage resources

The Stage resources tab controls how much Slurm time, CPU, and memory each workflow stage requests. These settings do not directly change the model physics, but they strongly affect whether the run waits in the queue, finishes successfully, or gets killed for running out of time or memory.

The workflow is split into three stages: preprocessing, the SFINCS solver, and postprocessing. Each stage can have different resource needs, so the page keeps their requests separate.

Field group What it controls How to think about it
preprocess_time, preprocess_nodes, preprocess_ntasks, preprocess_cpus_per_task, preprocess_mem Resource requests for the preprocessing stage. Preprocessing builds or assembles model inputs. It may be light for small tests, but can become heavier when creating subgrid data, reading large rasters, or processing large forcing datasets.
sfincs_time, sfincs_nodes, sfincs_ntasks, sfincs_cpus_per_task, sfincs_mem Resource requests for the actual SFINCS solver stage. This is normally the main compute stage. CPU count matters most here, but requesting more CPUs only helps if the solver is actually configured to use them efficiently.
postprocess_time, postprocess_nodes, postprocess_ntasks, postprocess_cpus_per_task, postprocess_mem Resource requests for the postprocessing stage. Postprocessing makes summaries, maps, quicklooks, and plots. It can need extra memory for large result files or full-domain map products.
*_time The maximum wall time Slurm allows for that stage. Use shorter times for small tests and longer times for full runs. If the time limit is too short, Slurm can stop the job even if the setup is otherwise correct.
*_nodes and *_ntasks How the stage is placed on the cluster. Most normal single-model runs use one node and one task per stage. Change these only if the backend workflow actually supports a different layout.
*_cpus_per_task How many CPU cores are requested for one task. This is most important for the solver stage. For preprocessing and postprocessing, extra CPUs only help if those stages use parallel work.
*_mem The memory request for each stage. Too little memory can kill a job. Too much memory may make the job harder to schedule. Increase memory when working with larger domains, larger outputs, or heavier plots.
sfincs_use_openmp_threads Whether the solver should use OpenMP-style threading. Usually keep this true when requesting multiple CPUs for SFINCS. Otherwise the job may reserve CPUs that the solver does not use.
sfincs_omp_proc_bind and sfincs_omp_places Advanced OpenMP placement and binding settings. Most users should leave these alone. They control how solver threads are placed on CPU cores and are mainly useful for performance tuning.

Resource habit: start with conservative test resources, check actual CPU and memory use after the jobs finish, then adjust. Resource requests are not a badge of speed; they should match what the stages actually use.

4 — Data catalogs

The Data catalogs tab tells the backend and HydroMT-style setup where to find named datasets, source files, and curated event inputs. A catalog is not usually the data itself; it is a map that lets the workflow find data by name.

This is one of the most important setup fields because later tabs may refer to sources by catalog name. If the needed catalog is missing, a setting can look correct on the page but still fail when the backend tries to resolve it.

Field / behavior What it means How to use it safely
data_catalogs A JSON list of catalog names or catalog paths available to the run. Keep valid JSON syntax. A single catalog should still be written as a list, such as ["catalog_name"].
Catalog names Short names that the backend knows how to resolve in the current deployment. Use these only when the project environment defines them. If the launcher is moved to a new project folder, names may need to be updated or replaced with explicit catalog paths.
Catalog paths Full paths to catalog files or folders visible to the backend. Use paths that exist from the server or cluster point of view. A path on your laptop will not work unless it is also available to the backend.
Browse button Uses the launcher path browser to choose catalog paths from allowed locations. Prefer browsing over manual typing when possible. It reduces typos and helps keep paths inside allowed roots.
Catalog order The order in the list can matter when multiple catalogs define similar source names. Put the intended project or event catalog where the backend expects it. Avoid leaving old test catalogs in the list unless deliberately testing.

Important: selecting a catalog does not automatically prove every forcing file covers the model time window. Runtime-window review can catch some catalog-level timing problems, but deeper file-by-file forcing coverage checks are a separate validation layer.

5 — Required inputs

The Required inputs tab defines the minimum spatial inputs needed to build a Manual Mode model. This is where you describe the model region and tell the setup where elevation or topobathy information should come from.

These settings are upstream of almost everything else. If the region, coordinate interpretation, or elevation source is wrong, the rest of the run can look organized but still represent the wrong physical model.

Field What it controls How to use it safely
region_mode Chooses how the model region is defined. Use geom when providing a region geometry path. Use bbox when defining the region by bounding box values.
region_path A geometry file or dataset that defines the model region. Use this when the model area should follow a saved polygon or geometry. The path must be visible to the backend, not just to your local computer.
region_bbox A bounding-box definition of the model area. Use this only when the coordinate order, units, and coordinate reference system are clear. A bounding box in the wrong CRS can place the model in the wrong location.
dem_paths A JSON list of direct elevation or topobathy file paths. Use direct paths when you have specific files that should supply elevation/depth information. Keep units and vertical datum assumptions consistent.
hydromt_dem_sources A JSON list of catalog-based DEM or elevation source definitions. Use this when elevation data should be pulled from named catalog sources. The referenced source names must exist in the selected data catalogs.
require_at_least_one_forcing A safety check requiring at least one forcing family to be enabled. Keep true for normal runs. Turn it off only for deliberate scaffold tests or backend debugging where a no-forcing model is expected.

Model-building note: Required inputs are about defining the physical model area and base elevation information. Event-specific drivers such as rainfall, water levels, and discharge are handled later in the Model settings and Forcing tabs.

6 — Optional inputs

The Optional inputs tab adds extra spatial data, forcing helpers, observation locations, hydrography, roughness support, and structure layers. These inputs are called optional because a basic model can sometimes be built without them, not because they are unimportant.

In practice, many serious runs depend on optional inputs. For example, observation points are optional for running the model, but they are very useful for checking results. Structure layers are optional only if the model does not need those structures represented.

Field group What it controls How to use it safely
bathy_paths and hydromt_bathy_sources Optional bathymetry or below-water elevation sources. Use direct paths when you have specific bathymetry files. Use catalog source definitions when the data should be resolved through the selected data catalogs. Check units, horizontal CRS, and vertical datum before mixing bathymetry with land elevation.
landcover_path, landcover_source, and landcover_reclass_table Optional land-cover information used by roughness or other spatial parameter mapping. Use these when the setup should derive parameters from land-cover classes. The reclass table or mapping must match the land-cover product being used; otherwise class values may be interpreted incorrectly.
hydromt_roughness_sources Catalog-based roughness source definitions. This belongs with roughness workflows that resolve sources by name through a catalog. Leave it empty unless the roughness setup is expected to use catalog-defined sources.
rainfall_path, rainfall_source, and rainfall_variable Optional rainfall source hints or direct rainfall input settings. These fields can describe where rainfall comes from, but the actual rainfall behavior is controlled later by the Model settings and Forcing tabs. Do not assume a rainfall path is used unless rainfall is enabled and the chosen rainfall kind matches the source.
waterlevel_path, waterlevel_source, and waterlevel_variable Optional water-level boundary source hints or direct water-level input settings. Use these only when the selected boundary workflow expects them. Water-level forcing must match the model boundary locations and the model time window.
discharge_source, streamflow_site_info_path, and streamflow_data_path Optional discharge or streamflow source information. Discharge setup often needs both site metadata and time-series data. A source name alone is not enough unless the selected catalog already knows how to resolve the full discharge dataset.
hydrography_path and hydrography_source Optional river, stream, or hydrography network information. Use these when the build workflow needs a river network for source placement, subgrid river handling, drainage interpretation, or other network-aware setup steps.
obs_points_path and obs_lines_path Observation point and observation line locations for history output. These do not force the model. They tell SFINCS where to save time-series output for gauges, points, transects, or cross-section-like lines. Enable them when you want hydrographs or validation-friendly output.
thin_dam_source_kind and thin_dam_path Optional thin-dam structure input. Use none when not using thin dams. Use a geodataframe-style source when the backend should process spatial vector data. Use native SFINCS only when the backend truly supports that native file path in Manual Mode.
weir_source_kind and weir_path Optional weir input. Weirs can strongly affect flow paths. Only enable them when the source data is intentionally prepared for this model domain and the backend supports the selected source style.
drainage_structure_source_kind and drainage_structure_path Optional drainage-structure input. Drainage structures should not be enabled just because a path exists. The structure format, coordinate system, and backend support all need to match the selected source kind.
culvert_source_kind and culvert_path Optional culvert input. Culverts can add connectivity that the grid alone may not represent. Use them only when the culvert dataset has been prepared for the model and the backend knows how to translate it.

Safe habit: optional input paths should usually stay blank unless the matching model toggle, source kind, or backend workflow will actually use them. A filled path does not automatically mean the feature is active.

7 — Model settings

The Model settings tab defines the model grid, model clock, and major physics/feature toggles. This tab connects the physical model domain to the event being simulated.

These settings are high impact. A run can pass basic page checks but still be scientifically wrong if the time window, grid, CRS, or forcing toggles do not match the intended event and input data.

Field group What it controls How to use it safely
grid_resolution_m A general target resolution for the model setup. Treat this as a broad resolution target. Finer resolution can represent more detail, but it also increases model size, runtime, output size, and preprocessing cost.
grid_dx_m and grid_dy_m The model grid spacing in the x and y directions. Keep these consistent with the intended model resolution. A small cell size over a large region can create an expensive run very quickly.
grid_crs The coordinate-reference-system setting or label used by the build workflow. Use a CRS appropriate for the region and units. Projected meter-based grids are usually easier to reason about for cell size, distance, and area than latitude/longitude grids.
grid_rotated and grid_rotation_deg Whether the model grid is rotated and, if so, by how many degrees. Use rotation only when it is intentional. Rotated grids can fit a domain efficiently, but they make map interpretation and some debugging steps more complicated.
tref The model reference time. This anchors model time. Keep it consistent with the event and with the time conventions expected by the backend and SFINCS inputs.
tstart and tstop The model simulation start and stop times. These should cover the event period you want to simulate. They also need to make sense relative to rainfall, boundary, discharge, wind, pressure, and observation time ranges.
use_rainfall Turns rainfall forcing on or off. Set true only when the Forcing tab is configured to provide valid rainfall or when the selected catalog/source supplies it. The toggle enables the family; it does not create rainfall data by itself.
use_waterlevel_boundary Turns water-level boundary forcing on or off. Set true when the model has boundary locations and matching water-level time series. Boundary geometry and boundary forcing need to agree.
use_discharge_boundary Turns discharge or source-flow forcing on or off. Set true when discharge locations and discharge time series are configured. For CSV-style discharge, point metadata and time-series columns must line up.
use_infiltration Turns infiltration or runoff-loss behavior on or off. Set true only when the Infiltration tab is configured for the intended method. Infiltration method and infiltration inputs should agree.
use_wind and use_pressure Turns atmospheric wind and pressure forcing on or off. Keep false unless the run is intentionally using these forcings and the Forcing tab has valid backend-visible inputs for them.
use_structures Turns structure handling on or off. Set true only when structure source kinds and paths are configured intentionally. Structure settings in Optional inputs should support this choice.
use_obs_points and use_obs_lines Turns observation point and line output setup on or off. These are for extracting history output and validation-friendly time series. They require valid observation paths if enabled.

Key idea: the use_* toggles and the source/path fields must agree. Turning a feature on without supplying the matching data usually creates a bad setup, while filling a path without enabling the feature may do nothing.

8 — Elevation / mask

The Elevation / mask tab controls how the model turns elevation information into active cells, inactive cells, and boundary behavior. This is one of the most important geometry sections because it determines where water can exist and where water can enter or leave.

Mask settings can make a model look clean while silently removing important areas, disconnecting flow paths, or creating invalid boundaries. Treat these settings as physical model-building controls, not just display options.

Field What it controls How to use it safely
dem_zmin A minimum elevation or depth threshold used while preparing elevation data. Use this carefully when filtering elevation values. A threshold that is too aggressive can remove shallow or low-lying areas that matter for flooding.
elevation_buffer_cells The number of grid cells used as a buffer around elevation or active-area processing. A small buffer can help avoid edge artifacts. Too much buffering can expand processing beyond the intended area or make debugging harder.
active_zmin The elevation/depth threshold used to decide which cells are active in the model. This strongly affects the model mask. If the threshold is wrong, cells that should flood may be excluded, or cells that should be inactive may remain active.
mask_fill_area_km2 A cleanup threshold for filling small holes or gaps in the active mask. Useful for removing small artifacts, but a value that is too large can fill areas that should remain disconnected or inactive.
mask_drop_area_km2 A cleanup threshold for dropping small isolated active areas. Useful for removing tiny disconnected artifacts. Be careful not to drop real disconnected floodplain, channel, island, or coastal features that matter to the run.
waterlevel_boundary_zmax A threshold used when creating or resetting water-level boundary cells. This helps decide where water-level boundary behavior should apply. Check that the resulting boundary matches the intended open-water or coastal/river boundary areas.
reset_waterlevel_boundary Controls whether the water-level boundary is reset or recreated during setup. Use true when you want the workflow to regenerate the boundary from the current settings. Use false only when preserving an existing boundary is intentional.
outflow_boundary_polygon_path An optional polygon path used to define outflow boundary behavior. Use this only when you have a prepared geometry for outflow boundaries. The path must be visible to the backend and should match the model CRS or be safely reprojectable.
reset_outflow_boundary Controls whether outflow boundary cells are reset or recreated during setup. Use true when the outflow boundary should be generated from the current settings. Use false when intentionally preserving a boundary already prepared elsewhere.

Geometry check: after changing elevation or mask settings, inspect the generated model layout before trusting a run. A model can submit successfully even when the active mask or boundary placement is physically wrong.

9 — Roughness

The Roughness tab controls how much resistance the model applies to flowing water. In SFINCS-style flood modeling, roughness is commonly represented with Manning values. Higher roughness slows flow more; lower roughness allows water to move more easily.

Roughness can be simple, such as one uniform value, or more spatially detailed, such as separate land/sea values or land-cover-derived values. The best choice depends on the model purpose, available data, and how much spatial detail the run needs.

Field What it controls How to use it safely
manning_uniform A single fallback Manning roughness value. Use this as a simple baseline or fallback. It is easy to understand, but it cannot represent different surfaces such as roads, channels, wetlands, buildings, or open water.
manning_land The Manning value used for land areas when the setup separates land and water roughness. Use a value that makes sense for the land surface being modeled. A value that is too high may slow flood movement too much; a value that is too low may make water spread unrealistically fast.
manning_sea The Manning value used for sea, bay, channel, or open-water areas when land and water are separated. Usually this is lower than land roughness because open water often has less flow resistance than vegetated or built land areas.
roughness_land_level_m The elevation threshold used to separate land-style roughness from sea/open-water-style roughness. Use this carefully because it controls which cells are treated as land versus water for roughness purposes. It should be consistent with the elevation and vertical-datum assumptions in the model.
use_landcover_roughness_if_available Controls whether land-cover-based roughness should be used when land-cover inputs are available. Set true only when the land-cover source and reclassification/mapping are valid for the run. If land-cover mapping is incomplete or mismatched, a simpler roughness setup may be safer.

Safe habit: roughness choices should match the surface data actually being used. Do not assume a land-cover path changes the model unless the roughness workflow is configured to use it.

10 — Subgrid

The Subgrid tab controls whether the model uses finer elevation and roughness detail inside each coarser model cell. Subgrid data can make a relatively coarse model represent small-scale topography more realistically, but it also adds preprocessing cost and file complexity.

Think of the main grid as the computational grid and the subgrid as extra detail stored inside those cells. This can be very useful for flood modeling, but only when the elevation, roughness, and subgrid settings are internally consistent.

Field What it controls How to use it safely
use_subgrid Master toggle for using subgrid data. Keep true when the run is intended to use subgrid tables. Set false only for model setups that are meant to run without subgrid detail.
subgrid_source_kind Chooses whether subgrid data is generated, supplied from a pre-made file, or not used. Use hydromt_generate for the normal Manual-style path. Use premade_sbgfile only when backend support for that path is confirmed. Use none only when subgrid should be skipped.
subgrid_native_file_path A path to a pre-made native subgrid file when using the pre-made subgrid option. This should stay blank unless subgrid_source_kind is set to use a pre-made file and the backend really copies or links that file correctly into the run setup.
subgrid_nr_pixels The number of fine subgrid pixels represented within each main model cell. Higher values can capture more detail but increase preprocessing work and output size. Use a value that matches the available source-data resolution and the run size.
subgrid_write_dep_tif Controls whether a diagnostic elevation/depth GeoTIFF is written during subgrid creation. Useful for checking the generated subgrid surface. Turn it off only when you are confident in the setup or trying to reduce extra files.
subgrid_write_man_tif Controls whether a diagnostic Manning roughness GeoTIFF is written during subgrid creation. Useful for checking roughness mapping. This can help catch cases where land-cover or roughness classes are being interpreted incorrectly.
subgrid_use_rivers Controls whether river-network information should be used during subgrid creation. Use true only when river information is available and the backend workflow supports using it in subgrid generation.
subgrid_river_path A direct path to river-network data for subgrid generation. Use this when the run should use a specific river dataset. The path must be visible to the backend and suitable for the model region.
subgrid_river_source A catalog source name for river-network data. Use this when the river data should be resolved through the selected data catalogs. The source name must exist in those catalogs.
use_spatially_variable_roughness Controls whether spatially varying roughness is used with the subgrid setup. Keep this aligned with the Roughness and Optional inputs tabs. Spatially variable roughness is only useful when the required roughness or land-cover inputs are available.

Implementation caution: pre-made subgrid support should stay treated as a confirmed-backend feature, not just a visible dropdown option. A safe implementation must place the file where the run expects it and avoid conflicting with generated subgrid output.

11 — Forcing

The Forcing tab describes the time-dependent inputs that drive the model. Common forcing families include rainfall over the domain, water levels along boundaries, discharge at source points, and optional atmospheric inputs such as wind or pressure.

The feature toggles in Model settings decide which forcing families are active. The Forcing tab explains where those active inputs come from and how they should be interpreted.

Field group What it controls How to use it safely
rainfall_kind Chooses the rainfall input style. Use spatial for gridded or catalog rainfall, uniform for one constant rainfall rate, and event/catalog options only when the selected catalog provides that event rainfall.
rainfall_uniform_mm_hr The constant rainfall rate used when rainfall kind is uniform. Only matters for uniform rainfall. Leave blank or null when rainfall is not uniform.
rainfall_clip_to_model_time Controls whether rainfall data is clipped to the model start/stop window. Usually keep true. Clipping helps prevent extra forcing data outside the run period from confusing the setup.
waterlevel_source_kind Chooses the source style for boundary water-level forcing. Use catalog or dataset styles when the backend should build boundary forcing. Use CSV when providing table-like time series. Native SFINCS options are usually better handled through Override Mode unless Manual support is intentionally confirmed.
waterlevel_clip_to_model_time Controls whether water-level forcing is clipped to the model time window. Usually keep true. The boundary time series should cover the simulated event period and match the boundary locations.
discharge_source_kind Chooses the source style for discharge or source-flow forcing. Use catalog/dataset styles when discharge is resolved through a catalog. Use CSV when providing source-point metadata and discharge time series directly. Native SFINCS options belong mainly in Override Mode unless Manual support is confirmed.
discharge_clip_to_model_time Controls whether discharge forcing is clipped to the model time window. Usually keep true. Discharge should cover the simulated period and align with the intended source locations.
discharge_points_csv_path Path to a CSV describing discharge/source point locations. Use this for direct CSV discharge workflows. The file should identify where each source point is located.
discharge_points_x_column, discharge_points_y_column, and discharge_points_name_column Column names used to read source-point x/y coordinates and source names. These names must match the point CSV exactly. The names should also connect cleanly to the discharge time-series columns.
discharge_timeseries_csv_path Path to a CSV containing discharge values over time. Use this together with a source-point CSV. The time-series file should have one time column and one or more discharge value columns.
discharge_time_column The name of the time column in the discharge time-series CSV. The value should match the CSV column name exactly. The times should use a format the backend can parse.
discharge_value_columns A JSON list of discharge value columns to use. An empty list can mean all non-time columns, depending on backend behavior. Use an explicit list when you want to control exactly which source columns are used.
discharge_time_format How discharge timestamps should be parsed. auto is usually safest for common timestamp formats. Use a specific format only when the CSV requires it.
discharge_units The units of the discharge values. Make sure the values use the units expected by the backend and model setup. Unit mistakes can make a run look successful while producing physically wrong results.
meteo_update_interval_s The update interval for meteorological forcing. Use a value consistent with the temporal resolution of the forcing data. Too coarse may miss variation; too fine may imply precision the data does not have.
wind_path and pressure_path Optional direct paths to wind and pressure forcing inputs. Leave blank unless wind or pressure is enabled and the run has backend-visible files prepared for those forcing families.
wind_source and pressure_source Catalog source names for wind and pressure forcing. Use these only when the selected data catalogs define those sources and the Model settings tab enables the matching forcing family.

Safe habit: forcing setup needs three things to agree: the model time window, the selected forcing kind, and the actual source/path fields. A filled path is not enough by itself, and an enabled toggle is not enough by itself.

12 — Infiltration

The Infiltration tab controls how rainfall is reduced by soil storage, infiltration capacity, or runoff-loss assumptions before it becomes surface water in the model. Infiltration can be disabled, represented simply, or supplied through more detailed spatial inputs.

This section matters most for rainfall-driven flooding. If rainfall is disabled, infiltration settings may have little or no effect. If rainfall is enabled, the infiltration method should match the available data and the assumptions of the run.

Field group What it controls How to use it safely
infiltration_mode Chooses the infiltration method. Use none when infiltration should be disabled. Use constant or spatial methods only when their parameters are set. Use curve-number methods only when the needed curve-number or soil inputs are available. Native SFINCS options usually belong in native-file workflows unless Manual support is confirmed.
qinf_mm_hr A constant infiltration rate, usually interpreted as millimeters per hour. Only meaningful for constant-style infiltration. Check units carefully because a unit mistake can strongly change runoff volume.
qinf_zmin_m A threshold related to where constant infiltration is applied. Use this only when the selected infiltration method expects it. It should be consistent with the elevation/depth convention used in the model.
scs_initial_abstraction_factor The initial-abstraction factor for SCS/curve-number style runoff behavior. This is a model assumption, not just a formatting value. Keep it consistent with the curve-number method being used.
infiltration_path A general direct path for infiltration input data. Use this when the backend workflow expects one prepared infiltration dataset. Leave blank when using a different method or catalog-based inputs.
curve_number_path Path to curve-number data. Use this for curve-number infiltration workflows. The spatial coverage, grid alignment, and meaning of class values should match the model setup.
hsg_path Path to hydrologic soil group data. Use this only when the selected curve-number or soil method expects hydrologic soil groups.
soil_storage_path Path to soil-storage information. Use when the method needs spatial soil-storage capacity. It should be consistent with the rainfall event and any initial-condition assumptions.
qinf_path Manual path to a prepared infiltration-rate file. Use only when the backend is expected to copy or reference a prepared infiltration-rate file for the run.
smax_path and seff_path Paths to maximum and effective/initial soil-storage files. Use together when the method needs storage capacity and starting storage state. These files should describe the same grid/domain convention.
ks_path Path to saturated hydraulic conductivity data. Use for methods that need conductivity. Check units and spatial meaning before running.
sigma_path and psi_path Paths to Green-Ampt-style parameter files. Use only when the selected infiltration method expects these parameters. Do not mix parameter families casually.
f0_path, fc_path, and kd_path Paths to Horton-style initial rate, final rate, and decay parameter files. Use these as a set when the selected infiltration method expects Horton-style behavior. The files should be prepared with consistent units and coverage.
vol_path Path to a prepared storage-volume file. Use only when the model setup expects an explicit storage-volume input. Leave blank for methods that do not use it.

Safe habit: choose one infiltration story and make the fields match it. Mixing curve-number, constant, Green-Ampt, Horton, and native-file inputs without a clear method can create a config that is technically filled out but physically unclear.

13 — Output

The Output tab controls what SFINCS writes while the model is running. These settings affect file size, runtime, postprocessing cost, and what kinds of results can be inspected later.

More output is not always better. Very frequent map output can create large NetCDF files and make postprocessing slower or more memory-heavy. A safer habit is to save enough output to answer the question being studied, without writing unnecessary full-domain snapshots.

Field What it controls How to use it safely
output_format The general output format written by the model. Use the normal backend/SFINCS-supported format for the current workflow. Changing this can affect which output files postprocessing expects to read.
dtout_s The main map-output interval, in seconds. This controls how often full-grid map-style outputs are written. Smaller values give more time detail but can greatly increase file size.
dthisout_s The history-output interval, in seconds. This affects gauge, point, line, or cross-section time series. History output is usually much smaller than full map output and is useful for validation plots.
dtmaxout_s The interval or control for maximum-output products. Use this when the model should track maximum water level, maximum depth, or related summary-style outputs. It should make sense for the event duration.
dtrstout_s The restart-output interval, in seconds. Restart files are useful when you need to continue a run later. They can add storage cost, so leave this off or infrequent unless restart workflow is actually needed.
store_wet_duration Controls whether wet-duration information is stored. Useful when duration of inundation matters. It is less important for quick smoke tests or runs where only peak/final conditions are needed.
store_velocity Controls whether velocity output is stored. Velocity fields can be useful for flow interpretation, but they add output size. Enable when velocity maps or velocity diagnostics are needed.
store_max_velocity Controls whether maximum velocity is stored. Useful for identifying high-velocity hazards or comparing flow intensity. Keep enabled only when the postprocess/analysis needs it.
store_max_flux Controls whether maximum flux information is stored. Flux output can help diagnose flow pathways and structure/source behavior, but it is extra output. Enable intentionally.
store_cumulative_precip Controls whether cumulative precipitation is saved. Useful for rainfall-driven events and checking whether rainfall forcing accumulated as expected. It matters less when rainfall is disabled.
store_hmax_subgrid Controls whether subgrid maximum-depth style output is stored. Useful for subgrid flood-depth products. If the model is not using subgrid, this may not matter or may be ignored by the backend/model.

Output habit: choose output intervals based on the question you need to answer. For debugging, use lighter output. For final analysis, save enough map/history output to support validation and interpretation.

14 — Advanced

The Advanced tab is for raw configuration keys that are not represented by normal form fields. It is powerful because it can pass specialized backend or SFINCS settings through the launcher, but it is also one of the easiest places to create a hard-to-diagnose mistake.

Use this tab only when you know what the key does, why it is needed, and whether it belongs in Manual Mode. Normal users should usually leave Advanced Config alone unless they are following a tested template or debugging a specific backend option.

Field / concept What it controls How to use it safely
advanced_config A raw JSON-style configuration area for extra keys. Keep valid JSON syntax. A missing comma, quote, brace, or wrong value type can break preflight before a run even starts.
Advanced SFINCS controls Can include model-size, numerical, output, or specialized SFINCS settings not exposed elsewhere. Only add keys that the backend and SFINCS actually understand. A familiar-looking key from another workflow may not be valid in this one.
Backend-only controls Can include special runner or preprocessing settings if the backend schema supports them. Do not use Advanced Config to bypass page checks. If a setting is important and repeated, it should eventually become a normal field or schema-backed option.
Loaded old configs Advanced Config can preserve unusual settings from older saved configs. Review old keys carefully. A stale key may have made sense for a past version but no longer affect the current backend.

Rule of thumb: if you cannot explain what an advanced key changes in the final run folder or sfincs.inp, do not change it here.

15 — Postprocess

The Postprocess tab controls the human-readable products created after SFINCS finishes. These products help you quickly check whether the run completed, what variables were written, where water accumulated, and how observation points or lines behaved.

Postprocessing is not just decoration. It is the first QA/QC layer after a run. However, maps with basemaps, overlays, and large full-domain products can become memory-heavy, so these settings should match the size of the run and the purpose of the analysis.

Field group What it controls How to use it safely

postprocess_list_output_variables Writes a list of variables found in model output files. Keep enabled. It is one of the fastest ways to confirm what SFINCS actually wrote.
postprocess_make_quicklook_plots Master switch for making quicklook figures. Useful for normal runs. For very large domains or memory-limited tests, this can be disabled to reduce postprocess load.

postprocess_plot_obs_hydrographs Creates hydrographs from observation point or line history output. Requires history output and observation definitions. If no observations exist, this may do little or produce a warning.

postprocess_use_rotated_map_plots Controls whether plots respect rotated-grid layout. Use this when the model grid is rotated and you want plots to match the physical model orientation more accurately.

postprocess_max_plot_cells A safety limit for how many cells are plotted. Use this to prevent huge plots from overwhelming memory. Raise it only when the postprocess Slurm resources can support it.

Memory note: if a model run succeeds but postprocessing fails, the model may still be fine. Check SFINCS logs and output files, then reduce heavy plots or increase postprocess memory before rerunning postprocess.

16 — Safety / debug

The Safety / debug tab controls guardrails, logging, warnings, saved metadata, and schema behavior. These settings help prevent expensive or confusing mistakes before a run reaches Slurm.

Most safety settings should stay enabled for normal work. Turn them off only when you are deliberately debugging a specific failure and understand what protection you are bypassing.

Save/Load are convenience tools. You do not need to click Save Progress before a normal one-off preflight. Backend preflight receives the current page setup and records the run config/scaffold needed for that workflow.

Override

Override Mode is for runs where some or most of the SFINCS input files already exist. Instead of building everything from source data, you select native SFINCS files from a static folder and/or an event folder, let the launcher detect them, choose which ones to use, and then finish the remaining setup in a simplified manual-style workflow.

Static files vs. event files

Override Mode separates native SFINCS inputs into two practical groups: static files and event files. Static files describe the physical makeup of the model domain that is mostly constant in time. Event files describe the forcing or initial conditions for one specific storm, flood, tide period, or scenario.

This split matters because you often want to reuse the same physical model setup for many different events. For example, the topography, bathymetry, mask, roughness, boundary locations, source locations, and observation locations may stay the same, while the rainfall, water-level boundary, discharge time series, wind, pressure, or restart state changes event to event.

Static files

Static files describe things inherent to the model area or model design. These are the pieces that usually do not change just because the event changes.

Examples include topography/bathymetry, active-cell masks, grid index files, subgrid tables, roughness, infiltration layers, boundary/source geometry, observation points, cross-sections, and structures.

Event files

Event files describe what happens during a specific run period. These are usually time-dependent files or initial-state files.

Examples include water-level boundary time series, discharge time series, rainfall, wind, atmospheric pressure, wave-related forcing, and restart or initial water-level files.

Note: this Override guide focuses on the special file-detection and override workflow. For a deeper review of the normal launcher tabs and settings, use the Manual section of this guide.

How Override differs from Manual

Override Mode is basically Manual Mode with an extra native-file step at the beginning. In Manual Mode, you mostly enter settings directly. In Override Mode, you first choose static and/or event folders, detect native SFINCS files, and select which detected files should override the normal generated inputs.

After the override files are selected, the page becomes closer to a stripped-down Manual Mode. You still choose the run name, output folder, timing, resources, advanced settings, review checks, and submit behavior. The difference is that some settings may already be controlled by selected native files.

When a selected native file controls part of the setup, the matching manual control may become hidden, locked, or greyed out. This is intentional. It prevents the page from suggesting that a setting is editable when the chosen override file is actually controlling it.

Important: detecting a file is not always the same as using it. Detection finds possible files. The selected override list decides which files are actually copied into the run and pointed to by the generated sfincs.inp.

  • 7

  • 8

Step-by-step Override workflow

  1. Choose the static and/or event folders. Start by selecting the folder that contains the static native files, the folder that contains the event native files, or both. For example, a Harvey 2017 example might use a trusted static model folder plus a Harvey-specific event folder.
  2. Detect available native files. Use the detection button to scan the selected folders. This lets the page find files such as sfincs.dep, sfincs.msk, sfincs.bzs, sfincs.dis, and precip_2d.nc.
  3. Select the files you actually want to override with. Detection only finds candidates. The selected override list is what tells the launcher which native files should be copied into the run folder and referenced by the generated model input.
  4. Review fields that become hidden, locked, or greyed out. If a selected native file already supplies part of the model, the corresponding manual control may no longer matter. In that case, the launcher may hide it, lock it, or grey it out so the page does not imply that changing the field will affect the run.
  5. Set the run identity and output location. Choose a clear run name and a run output folder. The run folder is where the launcher writes the final config, scripts, logs, copied native inputs, SFINCS outputs, and postprocessing outputs.
  6. Check the timing and model settings. If a detected sfincs.inp is available, the launcher may use it to fill timing fields like reference time, start time, and stop time. Even when sfincs.inp itself is overridden, the model settings and advanced config area should stay visible because those settings are important to inspect before running.
  7. Set resources and submit behavior. Choose the Slurm resources for preprocessing, SFINCS, and postprocessing. The correct values depend on model size, event length, output frequency, and how heavy postprocessing will be.
  8. Use Advanced Config only for settings you understand. Advanced Config is for SFINCS keys or backend settings that are not exposed as normal page controls. This is useful for expert edits, but it expects valid syntax and assumes you know what the keys mean.
  9. Run the review checks. Before submitting, review the detected files, selected overrides, model timing, output folder, overwrite behavior, resources, and any warnings. Page-level checks are helpful, but the backend preflight is still the real check before a run should be submitted.
  10. Use Save/Load only when useful; then preflight, build, and submit. Save Config is mainly for pausing your work, making a reusable template, or coming back later with Load Config. You do not need to manually save before a normal run. Running backend preflight records the current page setup and creates the config/scaffold needed for the run workflow. Build Scripts prepares the Slurm scripts, and Submit launches the jobs. A scaffold is not completed model output; real outputs only exist after the jobs finish.

Save Config and Load Config

Save Config and Load Config are convenience tools, not required steps for every run. Use Save Config when you want to pause and come back later, create a reusable template, duplicate a setup, or share the setup with someone else.

Load Config restores a saved JSON setup back into the page. This is useful when you want to continue a previous setup without re-entering all folders, overrides, timing, resources, and advanced settings by hand.

For a normal one-off run, you do not need to click Save Config before running. Running backend preflight sends the current page setup to the backend and records the config/scaffold needed for that run workflow.

About sfincs.inp in Override Mode

sfincs.inp is different from the other native files because it controls the run settings and points to the other input files. In Override Mode, the safer pattern is usually to let the launcher generate a fresh sfincs.inp from the page settings, while using detected native files for the model inputs.

You may still use a detected sfincs.inp as a reference for timing or settings. Directly overriding sfincs.inp should be treated as an intentional reproduction choice, not the default beginner path.

Why the settings stay visible: even when sfincs.inp is selected or parsed, the model settings and Advanced Config areas remain visible so you can inspect important values before running.

Advanced Config

Advanced Config is a raw settings area for keys that are not represented by the normal page controls. Use it for deliberate SFINCS or backend settings that you understand, such as projection behavior, numerical controls, output options, or specialized forcing switches.

The main rule is simple: if you are not sure what a key does, do not change it here. A typo, wrong value type, missing comma, or outdated setting can change the run or make it fail before SFINCS starts.

Review checks

The review section is the “slow down and check yourself” part of the workflow. It should summarize the run name, output folder, selected static/event folders, detected files, selected overrides, timing, resources, overwrite behavior, and any warnings.

These warnings are general checks. They do not mean every run is wrong, but they point to things that deserve attention before you submit. Missing file pointers, suspicious empty fields, invalid JSON, overwrite warnings, and mismatched static/event choices should not be ignored.

Review item What it is checking Why it matters
Run name and output folder Where the run will be written. Prevents accidentally overwriting or confusing runs.
Static/event folder choices Which native files are being pulled from which folders. Prevents mixing the wrong physical setup with the wrong event.
Selected override files Which detected files are actually active overrides. Detection alone does not mean a file is being used.
Timing fields Reference time, start time, stop time, and output intervals. Bad timing can make forcing files misalign or shorten the run accidentally.
Advanced Config Raw advanced settings and JSON syntax. A typo or invalid value can break the run or change model behavior.
File-pointer checks Whether files referenced by sfincs.inp will exist in the run folder. SFINCS should not be submitted with missing declared inputs.

Preflight, build scripts, and submit

The submit section turns the reviewed page settings into backend actions. Treat Preflight, Build Scripts, and Submit as separate steps, not one giant button.

Run backend preflight first. Preflight validates the current setup and records the config/scaffold needed by the run workflow. Build Scripts then prepares the Slurm scripts. Submit launches the Slurm chain.

Button / action What it does What to check
Preflight Runs backend validation and records the current page setup for the run workflow. Fix errors before moving on. Warnings should be read, not skipped blindly.
Build scripts Creates the run-folder scaffold and Slurm scripts. A scaffold is normal. It is not completed model output.
Submit Submits the Slurm workflow for preprocessing, SFINCS, and postprocessing. Only submit after the config, review checks, and output folder look correct.
Check status/logs Looks at job status, launcher logs, Slurm logs, and model outputs. If a job fails, logs are usually the fastest way to identify the failed stage.

Scaffold vs. real output: after Build Scripts, it is normal to see folders like scripts, logs, model, and postprocess. That does not mean the model has run yet. Real outputs appear only after the submitted jobs complete.
